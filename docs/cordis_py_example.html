示例应用解析：插件化多租户任务 API

FastAPI + cordis_py 的接近生产案例 —— 相比传统写法的变化、亮点与扩展方向

1. 案例是什么

一个多租户任务管理 API：任务 CRUD、API Key 认证、租户数据隔离、 限流、审计日志、指标计数、健康检查——全部能力由 9 个插件以声明式配置装配， 装配文件就是架构图：

# app.yml（完整装配配置）
plugins:
  - id: logger      # log 服务：带格式化的标准库 logger
  - id: tasks       # 业务 CRUD —— 刻意放在 http / tenant 之前（响应式依赖）
  - id: tenant      # 每租户 isolate("tasks", realm) + 专属任务存储（version=1.0）
  - id: http        # gate 中间件 + 路由注册表 + http/request 瀑布链
  - id: auth        # X-Tenant / X-API-Key → request.state.tenant（公开路径白名单）
  - id: quota       # 瀑布链监听：超标短路返回 429
  - id: audit       # 事件监听：task/created、task/deleted → 日志
  - id: metrics     # 计数服务 + /api/metrics 路由
  - id: health      # /api/health（公开）

主程序只有约 40 行：宿主创建 FastAPI 应用、注入运行时对象、加载配置、按需开启 HMR。

定位：cordis_py 是元框架（不内置 Web），本案例演示的是 “宿主（FastAPI）+ 插件（Cordis 语义）” 的落地形态——这不是特例，而是约定： 任何具体框架都可以坐在同一个插件内核之上。

2. 与传统写法的对比

维度传统 FastAPI 应用本案例（Cordis 插件化）
装配 main.py 里逐个 import、实例化、按顺序初始化；新增能力 = 改主程序 app.yml 声明即装配；新增能力 = 装插件 + 改配置，主程序不动
依赖顺序 先定义后使用；初始化顺序错误 = 启动期崩溃或 None 传递 声明依赖（inject/require），提供者后出现也能自动激活——顺序无关
中间件 固定栈（写在应用级，只能静态叠加）；策略逻辑与框架耦合 事件瀑布（waterfall）——每个插件是一环，不调用 next() 即拦截
副作用 注册了就"无处可去"；删除功能 = 动手术 一切可逆：路由/服务/监听器随插件 fiber 销毁，无残留
租户 if tenant == "acme" 分支、表名前缀、客户端定制三选一 realm 作用域隔离：同名服务在 (realm, name) 键上互不可见
开发 uvicorn reload = 全进程重启；状态丢失、启动 3 秒起 HMR：精确热替换受影响插件（依赖图分类），失败自动回滚
契约 DI 容器只解引用；升级不兼容 = 运行时 AttributeError @require 版本/接口约束，不满足时软等待——护栏提前到声明期

3. 亮点

3.1 九行配置 = 整个应用的架构图

传统工程里"看架构"要读主程序 + 所有 import；这里一份 YAML 即全景， 且每行都经过 Config 校验（callable / pydantic 可选）。

3.2 装配顺序无关（响应式依赖）

app.yml 中 tasks 排在 http / tenant 之前： 加载时因 routes / tenants 服务缺失而软等待，提供者出现后 自动激活并完成路由注册。生产收益：组件可以任意顺序发布，组合自动化、可演化。

@inject(["routes", "tenants"])      # 声明依赖
@require("tenants", ">=1.0")       # 版本契约：不满足则等待
def plugin(ctx, config):
    routes.add("POST", "/api/tasks", create_task)   # 激活时注册，dispose 时卸载

3.3 可逆副作用：卸载即"无痕"

路由、服务、事件监听器全部登记为 fiber 效果：插件重载/HMR 时旧 fiber dispose， 路由自动移除、监听器自动摘除、服务自动注销——不会出现“改了一半”的应用状态。

3.4 事件瀑布链 = 可插拔中间件

每请求只跑一条 http/request 链：认证 → 限流 → …… → 真实处理。 加"签名校验、风控计费"就是往链上挂一个插件，不改应用、不进 FastAPI 中间件栈。

def check(tenant, request, next_):
    if over_limit(tenant):
        return JSONResponse({"error": "rate_limited"}, status_code=429)
    return next_()          # 不调用 next_：整链短路

3.5 per-realm 租户隔离是"物理"的

每个租户建立独立 realm：ctx.isolate("tasks", "acme") 后 provide("tasks", store) —— 服务在 (realm, name) 键上查找。 globex 的请求**纯凭作用域就无法看到** acme 的数据，而不是靠业务代码里加一个 if tenant == ... 的约定。

3.6 宿主与插件的边界清晰

FastAPI 应用对象由宿主注入（root.provide("fastapi_app", app)）， 插件只消费——核心包零 Web 依赖；将来桥接 aiohttp / Quart / CLI 只是一层新插件。

3.7 开发期：改代码不重启

--watch 下修改 plugins/quota.py：1.5 秒内限流窗口重置、 新消息生效——旧插件被整体替换（含闭包状态），且支持编辑器原子保存 （临时文件 + rename，如 sed -i / Vim）。

4. 关键代码走读

4.1 宿主（main.py）：应用与插件的唯一接缝

@asynccontextmanager
async def lifespan(app: FastAPI):
    root = Context()
    root.provide("fastapi_app", app)          # 宿主注入运行时对象
    loader = Loader(root)
    await loader.include(BASE / "app.yml")    # 声明式装配
    if getattr(app.state, "watch", False):
        hmr = HMR(loader)
        app.state.hmr_watcher = hmr.watch([str(BASE / "plugins")])
    yield
    # 退出：一切按 LIFO 可逆回收
    await loader.dispose(); await root.fiber.dispose()

4.2 http 插件：把请求变成一条瀑布

@inject(["fastapi_app", "log"])
def plugin(ctx, config):
    async def gate(request, call_next):
        rejected = (ctx.get("auth") or ...).authenticate(request)
        if rejected is not None: return rejected            # 401
        return await ctx.waterfall(
            "http/request", tenant, request,                # 插件链
            fallback=lambda *args: call_next(request),      # 链尾 = 真实处理
        )
    app.state.cordis_gate = gate                            # 宿主中间件读取
    ctx.effect(lambda: undo)                                # 卸载时移除
    ctx.provide("routes", RouteRegistry(app))

4.3 tenant 插件：realm 是数据边界的载体

def register(self, ctx, name):
    scoped = ctx.isolate("tasks", name)      # 独立 realm 的子上下文
    scoped.provide("tasks", TaskStore(name)) # 键 = (name, "tasks")
    self._scopes[name] = scoped

def store(self, name):
    return self._scopes[name].get("tasks")   # 经该租户作用域解析

5. 实测验证

真实 uvicorn 进程上的 curl 序列（127.0.0.1:8123）：

场景结果
GET /api/health（公开）200 {"status":"ok","tenants":["acme","globex"]}
GET /api/tasks（无凭据）401
acme 创建任务201 {"id":"acme-1",...}
globex 列出任务{"items":[],"count":0} —— 数据隔离
同租户第 6 次请求（limit=5）429 {"error":"rate_limited"}
GET /api/metrics{"taskapi.tasks.created":2,"taskapi.tasks.list":2}

HMR 实测：--watch 进程运行中，用 sed -i （原子保存）把 429 消息改为 rate_limited_v2 —— 1.5 秒后： 限流窗口重置（前 5 次 200）+ 第 6 次返回 429 rate_limited_v2。 进程 PID 未变，证明新代码经 HMR 到达，旧插件实例（含内存状态）被完整替换。

自动化：核心 103 个测试 + 案例 6 个集成测试（TestClient 全链路），ruff 全绿。

6. 还能如何扩展

6.1 插件生态化（最近的下一步）

discovery（entry points）已实现：插件包声明入口后 pip install 即被运行时发现——插件市场/共享能力库是自然的下一步， app.yml 无需 import 路径，只有插件 id。

6.2 存储替换：把 TaskStore 换成真数据库

存储实现与 usage 完全解耦：SQLite/PG 插件提供同名 tasks 服务 （可选 version 升级契约）；连接池、事务、迁移随插件 fiber 可逆回收 ——“测试环境换内存后端、生产换 PG”只是配置差异。

6.3 观测体系：从 print 到 OTel

审计插件监听业务事件、指标服务已就位——接入 OpenTelemetry 只需一个插件： 把 task/* 事件与 http/request 瀑布改写成 span/metric， 业务代码零改动。

6.4 多进程 / 多 worker：Bridge 共享服务

大模型调用、缓存客户端这类“昂贵连接”放主进程，worker 进程经 Bridge.proxy() 调用——比 multiprocessing 共享状态契约干净； 服务与事件语义跨进程保持一致。

6.5 请求级租户上下文：再细一层的隔离

在 create_scope + scope_target（0.7.0 已实现）之上： 每请求一个带 tag 的作用域，插件间事件只向上流、互不触发——多租户之外再叠加 “插件不可信”边界（配合 global_ 显式放行）。

6.6 配置派生：租户级覆盖不经代码

internal/config overlay（0.4.0）：按租户在上层改写插件配置 （限流阈值、功能开关、模型名），改配置不改插件——多租户 SaaS 的分层治理。

6.7 CLI 与工程化（路线图 P0）

cordis-py run/init：发现插件、装配、watch、优雅退出； 脚手架生成插件骨架（Config + effect + 测试模板）。

边界提醒：协调式隔离（事件/服务可见性）不是恶意代码的安全边界； OS 级沙箱与 Bridge 安全层属后续立项。
