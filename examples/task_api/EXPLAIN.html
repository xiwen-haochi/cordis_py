先记住三个词，后面全部围绕它们展开

插件（plugin）
一段函数 def plugin(ctx, config): ...，只做一件事。它通过 ctx 提供/消费“服务”。
服务（service）
挂在 ctx 上的命名对象（如 routes、auth、tenants）。插件之间只通过服务名交互，不互相 import。
装配（composition）
把插件列表（url + config）交给 Loader，由它按顺序装载。装配顺序不重要——这是本 example 刻意演示的核心。
为什么拆成这样，而不是写成一个 500 行的 app.py？

500 行的 app.py 里，改一个功能要通读全局；插件化的 app.py 里，改限流 = 改 quota.py，换认证 = 改一行配置，删日志 = 删一行配置。每个关注点一个文件、 一份配置、一组测试——这就是“可组合性”落到日常工程的样子。

§01cordis_py 是什么：项目的 10 个特点

cordis_py 是 Cordis（论文《A Programming Paradigm for Spatiotemporal Composability》/ Node.js 版 Cordis v4）的 Python 实现：面向动态系统的时空可组合性元框架。 它不帮你写业务，它帮你组织业务——让“装上去的东西一定能拆下来，且拆得干净”。 它面向三个痛点：功能装上容易拆下难、初始化顺序写死、扩展要改核心。

feature 01

一切可逆（可组合性的“时”轴）

插件注册的所有东西（服务、事件监听器、路由、后台任务）都是一条“效果”记录，卸载时按 LIFO 逐一回收。拆插件 = 零残留，不存在“旧路由还在”的僵尸状态。

feature 02

依赖响应式（可组合性的“空”轴）

插件声明 @inject([...]) 后，依赖没就绪就保持 PENDING（软等待），提供者一出现就自动激活。装配顺序无关，加/删/换插件都不用调整其他代码。

feature 03

声明式装配

Loader 读 JSON / YAML / TOML 配置文件，一份文件 = 整张架构图。增删能力 = 增删一行配置。

feature 04

服务即契约

provide(name, value, version=...) + @require("svc", ">=1.0")。依赖升级有护栏：约束不满足不报错、只软等待。插件间只认接口不认类，实现了也能换。

feature 05

事件系统（5 种派发模式）

emit（同步广播）、parallel、serial、bail、waterfall（中间件链：不调 next 即拦截）。还支持 receiver= 过滤与 global_ 旁路。

feature 06

空间隔离原语

isolate(name, realm) 做服务 realm 隔离（多租户物理隔离，而非 if 判断）；filtered(pred) + create_scope 做事件可见性隔离（不可信插件边界）。

feature 07

显式生命周期状态机

每个插件实例是一个 Fiber：PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED（失败进 FAILED）。状态可查询（fiber.unsatisfied 告诉你它在等谁）。

feature 08

同步 / 异步双模式

有事件循环时走 asyncio，没有时自动内联同步驱动；同步链路遇到必须异步的操作抛 AsyncRequiredError 给出明确边界，绝不静默丢弃。

feature 09

HMR 开发期热替换

改插件源码不重启进程：模块依赖图分类（accepted / declined）+ 事务式重载 + 失败回滚。本 example 默认开启，保存即生效。

feature 10

跨进程 Bridge + 零依赖核心

Bridge 支持跨进程服务代理与事件贯通（JSON-lines 协议）；核心仅依赖 packaging，PyYAML / watchdog / pydantic 均为可选 extras。

注意目录里没有的“三层”：没有 service/ 层、没有 router/ 层、没有 middleware/ 层

这是故意的：layers（层）是结构，plugins（插件）是能力。层会在代码里形成“必须按顺序放”的硬约束，插件则让每个能力自带依赖声明。所以目录就两个：宿主文件 + plugins/。

§03启动：main.py 逐段拆解

宿主只负责三件事：创建应用对象 → 注入 → 加载装配。它不知道任何插件的存在，插件也不知道它的存在——唯一的接缝是 root.provide("fastapi_app", app) 这一个服务名。

examples/task_api/main.pypython
"""多租户任务 API 案例：FastAPI + cordis_py 插件化装配入口。"""

from __future__ import annotations

import argparse
import sys
from contextlib import asynccontextmanager
from pathlib import Path

from fastapi import FastAPI

BASE = Path(__file__).resolve().parent

sys.path.append(str(BASE / "src"))

from cordis_py import HMR, Context, Loader

@asynccontextmanager
async def lifespan(app: FastAPI):
    """启动：宿主注入应用对象 → Loader 声明式装配 → 可选 HMR 监听。"""
    root = Context()
    # 运行时对象（FastAPI 应用）由宿主注入，不进配置文件。
    root.provide("fastapi_app", app)
    loader = Loader(root)
    await loader.include(BASE / "app.yml")
    app.state.cordis = root

    hmr: HMR | None = None
    if getattr(app.state, "watch", False):
        hmr = HMR(loader)
        app.state.hmr_watcher = hmr.watch([str(BASE / "plugins")])

    yield
    # 退出：可逆效果按 LIFO 全部回收（服务、路由、监听器、模块追踪器）。
    if hmr is not None:
        await app.state.hmr_watcher.stop()
        hmr.dispose()
    await loader.dispose()
    await root.fiber.dispose()

def make_app(watch: bool = False) -> FastAPI:
    """创建应用；*watch* 为 True 时启用插件源码热替换。"""
    app = FastAPI(title="Cordis Task API", version="0.1.0", lifespan=lifespan)
    # 静态安装中间件入口（不随插件装载变动），链路逻辑由 http 插件注册。
    from plugins.http_service import CordisGateMiddleware

    app.add_middleware(CordisGateMiddleware)
    app.state.watch = watch
    return app

def main() -> None:
    parser = argparse.ArgumentParser(description="Cordis 插件化任务 API 案例")
    parser.add_argument(
        "--watch", action="store_true", default=True, help="启用 HMR 插件源码热替换"
    )
    parser.add_argument("--port", type=int, default=8000)
    args = parser.parse_args()

    import uvicorn

    uvicorn.run(make_app(watch=args.watch), host="127.0.0.1", port=args.port)

app = make_app()

if __name__ == "__main__":
    main()

3.1 逐段注释

1
L12–14：BASE 与模块路径

BASE = Path(__file__).resolve().parent = 本文件所在目录（examples/task_api/）。第 14 行把 BASE/"src" 加入模块搜索路径——注意本仓库结构中该目录并不存在，所以这一行实际不生效（把一个不存在的目录 append 进 sys.path 是安全的空操作）；from cordis_py import ... 能成功，依赖的是已安装的 cordis_py（仓库根 pip install -e . 的可编辑安装）。保留这行的意义：把示例目录拷到别处单独运行时，如果旁边放一份 src/ 源码即可免安装直跑。

2
L19–27：lifespan（FastAPI 生命周期钩子）

root = Context() 创建根容器；root.provide("fastapi_app", app) 把运行时对象注入容器——注意：它不进配置文件，因为 YAML 里放不了 Python 对象，这就是“宿主注入”的接缝。然后 Loader(root) 读 app.yml 并 await loader.include(...) 完成全部装配。

3
L29–32：可选 HMR

app.state.watch 由 make_app(watch=) 决定（main() 里默认 True，测试里 make_app() 默认 False）。开启后用 HMR(loader) 追踪模块依赖图，并 watch plugins/ 目录。

4
L34–40：yield 之后的清理（逆序回收）

先停 watcher、卸 HMR 追踪器，再 loader.dispose()（反向卸载全部插件 fiber，每个 fiber 的 effects 按 LIFO 清理），最后 root.fiber.dispose() 清根容器。顺序：先停“会触发变化的东西”，再拆插件，最后清容器。

5
L43–51：make_app —— 为什么中间件是“静态”装的？

FastAPI/Starlette 的中间件栈在应用启动时构建，运行中 add_middleware 会报 Cannot add middleware after application started（TestClient 触发生命周期时尤其明显，本项目的血泪教训）。所以入口中间件 CordisGateMiddleware 由宿主静态安装，而链路逻辑（认证 → 瀑布 → 真实处理）由 http 插件在 lifespan 内注册到 app.state.cordis_gate——中间件是固定的“电线”，插件是“电器”。

6
L54–70：入口 + 模块级 app

main() 解析 --port 后交 uvicorn；模块级 app = make_app() 允许 uvicorn main:app 或有 WSGI 网关的场景直接加载（此时 watch=False，不启动 HMR）。

为什么是“注入”而不是“导入”？

如果 http 插件直接 from main import app，就形成了 插件 → 宿主 的硬依赖：example 的入口换成一个纯 CLI 工具、一个爬虫、或一份测试，这个插件都得改。反过来，插件只声明 @inject(["fastapi_app"])，谁来提供都行——宿主输送到容器，插件从容器取，方向单向，谁都不认识谁。

§05插件逐个拆解（10 个文件）

每个插件都遵守同一个形状：def plugin(ctx, config) →（可选地）提供服务 / 监听事件 / 注册效果。下面按“它提供什么 → 它依赖什么 → 关键代码”的顺序讲。

5.1 logger_plugin.py —— 唯一“给所有人用”的基础服务

plugins/logger_plugin.pypython
def plugin(ctx: Context, config: dict[str, Any]) -> None:
    """注册 ``log`` 服务：``logger = ctx.get("log")`` 后按需取子 logger。"""
    level_name = str(config.get("level", "INFO")).upper()
    level = getattr(logging, level_name, logging.INFO)

    def get_logger(name: str = "cordis") -> logging.Logger:
        logger = logging.getLogger(name)
        if not logger.handlers:
            handler = logging.StreamHandler()
            handler.setFormatter(logging.Formatter(_FORMAT))
            logger.addHandler(handler)
            logger.propagate = False
        logger.setLevel(level)
        return logger

    ctx.provide("log", get_logger)
  • 提供：log 服务——值是一个工厂函数（不是 logger 实例）。这样任何插件可以 ctx.get("log")("quota") 拿到自己名字的 logger，避免共享同一 logger 名。
  • 亮点：服务值可以是任意 Python 对象，函数当然也可以。这是“服务 = 接口”的体现：消费方只知道可调用，不知道内部用 stdlib。

5.2 http_service.py —— 全示例最核心的插件

它做三件事：提供 routes、提供 app、装配请求 gate。先看 RouteRegistry——这是“可逆路由”的载体：

class RouteRegistry:
    """FastAPI 路由注册表：同名 (method, path) 可整体替换（重载安全）。"""
    def __init__(self, app: FastAPI) -> None:
        self._app = app
        self._routes: dict[tuple[str, str], Any] = {}

    def add(
        self, method: str, path: str, handler: Callable[..., Any], *, name: str | None = None,
    ) -> Callable[[], None]:
        """注册路由并返回卸载函数；已存在同名路由时先移除旧条目。"""
        key = (method.upper(), path)
        old = self._routes.get(key)
        if old is not None and old in self._app.routes:
            self._app.routes.remove(old)
        route = self._app.add_api_route(
            path, handler, methods=[method.upper()], name=name or handler.__name__
        )
        self._routes[key] = route

        def undo() -> None:
            if self._routes.get(key) is route:
                self._routes.pop(key, None)
                if route in self._app.routes:
                    self._app.routes.remove(route)

        return undo
为什么 router 也插件化？为什么不用 FastAPI 自带的 APIRouter？

APIRouter 一旦 include_router 就没有“取消”操作——HMR 重载业务插件时，旧路由会留在应用里变成僵尸（404 文档里出现、路由重复注册报错）。RouteRegistry.add 返回一个 undo 闭包：注册与注销成对出现，重载时先 undo() 旧的、再注册新的，同名路由整体替换。这是“效果可逆”在 Web 层面的直接应用，也是本 example 相对传统 FastAPI 工程最大的差异点。

再看 plugin() 主体——gate 链路：

plugins/http_service.py · pluginpython
@inject(["fastapi_app", "log"])
def plugin(ctx: Context, config: dict[str, Any]) -> None:
    app: FastAPI = ctx.fastapi_app
    logger = ctx.log("http")
    routes = RouteRegistry(app)

    async def gate(request: Request, call_next: Callable[..., Any]) -> Response:
        # 认证插件可缺省：不存在时直通。
        auth = ctx.get("auth")
        if auth is not None:
            rejected = auth.authenticate(request)
            if rejected is not None:
                return rejected
        tenant = getattr(request.state, "tenant", None)
        # 瀑布链：插件中途拦截（如限流）则直接返回；链尾执行真实处理。
        return await ctx.waterfall(
            "http/request",
            tenant,
            request,
            fallback=lambda *args: call_next(request),
        )

    # gate 由宿主中间件在请求期读取；插件卸载时移除（中间件恢复直通）。
    app.state.cordis_gate = gate

    def undo() -> None:
        if getattr(app.state, "cordis_gate", None) is gate:
            delattr(app.state, "cordis_gate")

    ctx.effect(lambda: undo)

    ctx.provide("routes", routes)
    ctx.provide("app", app)
    logger.info("http service ready: %s", config.get("title", "Cordis API"))
  • gate 是真正的请求入口：先认证（可选服务）→ 拿租户 → 走 http/request 瀑布 → 链尾 = call_next（把控制权交回 FastAPI 栈，命中路由）。
  • ctx.get("auth")：认证是可选服务——没装认证插件就直通。这就是“能力可插拔”在安全层上的表达。
  • ctx.effect(lambda: undo)：注意是 lambda: undo（返回函数本身作为卸载逻辑），不是 lambda: undo()——后者会在注册的瞬间就把路由删掉、并因返回 None 让 fiber 什么都登记不到（效果账本为空，之后卸载时无事可做）。这是本项目最常踩的坑，§07.2 细讲。
  • ctx.provide("routes", routes)：注册表作为服务交给业务插件——业务插件 不需要 import RouteRegistry，只用名字 "routes" 调 .add(...)。

class TenantRegistry:
    def register(self, ctx: Context, name: str) -> None:
        """为 *name* 建立独立 realm 的服务作用域，并在其中提供 tasks 存储。"""
        scoped = ctx.isolate("tasks", name)
        store = TaskStore(name)
        # (realm=name, name="tasks") 与其它租户互不可见。
        scoped.provide("tasks", store)
        self._scopes[name] = scoped

    def store(self, name: str) -> TaskStore:
        """经该租户的隔离作用域解析任务存储（realm 服务查找）。"""
        scoped = self._scopes[name]
        return scoped.get("tasks")

def plugin(ctx: Context, config: dict[str, Any]) -> None:

    registry = TenantRegistry()
    tenants = list(config.get("tenants") or ())
    for name in tenants:
        registry.register(ctx, name)
    ctx.provide("tenants", registry, version="1.0")
  • ctx.isolate("tasks", name)：创建子上下文并指定：在这个作用域里，服务名 tasks 属于 realm name。于是全局服务的键变成 (realm, name)——("acme","tasks") 与 ("globex","tasks") 是物理上不同的键。
  • scoped.get("tasks")：从该租户的作用域解析，只能拿到自己的存储。租户隔离不是业务层的 if tenant == ... 约定，而是容器层的键空间隔离——globex 的请求即使代码写错也“看不见” acme 的数据。
  • provide(..., version="1.0")：给 tenants 服务打版本号，供消费方 @require 校验（见 5.7）。

5.4 auth.py —— 认证是一份“契约”，不是内置功能

plugins/auth.py · 要点python
class AuthService:
    def authenticate(self, request: Request) -> JSONResponse | None:
        if request.url.path in self._public_paths:
            # 公开路径（如健康检查）：免认证直通。
            return None
        tenant = request.headers.get("x-tenant")
        key = request.headers.get("x-api-key")
        if tenant and self._keys.get(tenant) == key:
            request.state.tenant = tenant
            return None
        return JSONResponse(
            {"error": "unauthorized", "tenant": tenant},
            status_code=401,
            headers={"www-authenticate": "X-API-Key"},
        )

def plugin(ctx: Context, config: dict[str, Any]) -> None:
    """注册 ``auth`` 服务（http 中间件缺省感知其存在）。"""
    public = frozenset(str(p) for p in config.get("public_paths") or ())
    ctx.provide("auth", AuthService(dict(config.get("keys") or {}), public))
  • 契约：authenticate(request) → JSONResponse | None——成功返回 None（并把租户写进 request.state.tenant），失败返回拒绝对象。gate 只认识这个接口，不认识 AuthService 这个类。
  • public_paths：白名单（本例只有 /api/health），公开路径直接放行且不绑定租户——所以健康检查不需要认证头。
  • 这为 §05.10 的 JWT 替换埋下伏笔：换认证 = 提供同名 auth 服务的另一个插件。

5.5 quota.py —— 瀑布链上的一环（拦路虎）

plugins/quota.pypython
def plugin(ctx: Context, config: dict[str, Any]) -> None:
    limit = int(config.get("limit", 5))
    window = float(config.get("window", 30))
    # 状态：租户 → [窗口起点, 已用次数]
    windows: dict[str, list[float]] = {}
    logger = ctx.get("log")

    def check(tenant: str | None, request: Request, next_: Callable[..., Any]) -> Any:
        # 公开路径（无租户绑定）的请求不限流（如健康检查轮询）。
        if tenant is None:
            return next_()
        now = time.monotonic()
        row = windows.setdefault(tenant or "<none>", [now, 0.0])
        if now - row[0] >= window:
            row[0], row[1] = now, 0.0
        row[1] += 1
        if row[1] > limit:
            if logger is not None:
                logger("quota").warning("rate limited tenant=%s", tenant)
            return JSONResponse(
                {"error": "rate_limited", "tenant": tenant}, status_code=429
            )
        return next_()

    # 瀑布链监听器：http 中间件每次请求都会运行本链。
    ctx.on("http/request", check)
  • 拦截语义：check 拿到 next_ 参数——超标时不调用 next_() 而是直接返回 429，链条短路。这就是“中间件 = 瀑布链上的可插拔环节”：不调 next 即拦截（对齐 Node Koa/Connect 思路）。
  • 可选依赖：ctx.get("log") 可能返回 None（logger 插件没装）——所以先判空再用。日志在 cordis 里是能力，不是基础设施。
  • 状态在插件闭包里：windows 字典是 plugin() 的局部变量。HMR 重载后旧变量随旧 fiber 一起被丢弃，计数自动归零——这是特性不是 bug（§07.6）。

5.6 audit.py —— 事件监听（解耦的旁观者）

plugins/audit.pypython
_EVENTS = ("task/created", "task/deleted")

def plugin(ctx: Context, config: dict[str, Any]) -> None:
    prefix = str(config.get("event_prefix", ""))
    logger = ctx.get("log")

    def audit(event: str, tenant: str, task: dict[str, Any]) -> None:
        if logger is not None:
            logger(f"audit.{event}").info(
                "%s tenant=%s task=%s", prefix, tenant, task.get("id")
            )

    for event in _EVENTS:
        # 监听器随本插件 fiber 回收（HMR 重载时自动清理）。
        # 注意默认参数绑定：避免闭包捕获循环变量。
        ctx.on(event, lambda *args, _event=event: audit(_event, *args))
  • 旁观者模式：audit 不认识 tasks，tasks 也不认识 audit。tasks 发事件 ctx.emit("task/created", tenant, task)，audit 只听自己关心的两个事件名——新增审计需求 = 新生效，不需要改业务代码。
  • 循环变量捕获坑：lambda *args, _event=event —— 把 event 做成默认参数在定义时快照。若直接 lambda *args: audit(event, *args)，循环结束后三个 lambda 都会读到最后一个 event（经典 Python 闭包坑）。
  • ctx.on(...) 返回的监听器自动进入当前 fiber 的效果账本：插件卸载/HMR 重载时监听器随之移除，不会留下“幽灵监听”重复触发。

5.10 jwt_auth.py —— 同契约替代实现（本示例的重点教学件）

它不是第 10 个插件，而是 auth 的替代件：与 AuthService 实现同一个契约 authenticate(request) → Response | None，因此 app.yml 里换一行 url 即可整体切换认证方式。

plugins/jwt_auth.py · 要点python
class JwtAuthService:
    def issue(self, tenant: str, *, ttl: int = 3600) -> str:
        """签发（管理端/测试用）：HS256 三段 JWT。"""
        header = {"alg": "HS256", "typ": "JWT"}
        payload = {
            "sub": tenant, "iss": self._issuer,
            "aud": self._audience, "exp": int(time.time()) + ttl,
        }
        signing = b".".join(
            (_b64(json.dumps(header).encode()), _b64(json.dumps(payload).encode()))
        )
        signature = hmac.new(self._secret, signing, hashlib.sha256).digest()
        return (signing + b"." + _b64(signature)).decode()

    def authenticate(self, request: Request) -> JSONResponse | None:
        # 契约入口：结构/签名/iss/aud/exp 任一不对 → 401；对 → state.tenant = sub
        if request.url.path in self._public_paths:
            return None
        header = request.headers.get("authorization", "")
        if not header.startswith("Bearer "):
            return self._reject("missing_token")
        parts = header[7:].split(".")
        if len(parts) != 3:
            return self._reject("invalid_token")
        signing = f"{parts[0]}.{parts[1]}".encode()
        expected = hmac.new(self._secret, signing, hashlib.sha256).digest()
        if not hmac.compare_digest(signature, expected):
            return self._reject("invalid_token")
        # ... 校验 iss / aud / exp，通过后：
        request.state.tenant = str(payload.get("sub") or "")
        return None

def plugin(ctx: Context, config: dict[str, Any]) -> None:
    """注册 ``auth`` 服务（同名契约，替换 api-key 认证）。"""
    ctx.provide("auth", JwtAuthService(secret=..., issuer=..., audience=..., public_paths=...))

切换三步：

  1. app.yml 里 auth 插件的 url 改为 plugins.jwt_auth:plugin；
  2. config 换为 secret / issuer / audience / public_paths；
  3. 请求头从 X-Tenant + X-API-Key 换成 Authorization: Bearer <token>（token 用 service.issue("acme") 签发）。

http 的 gate、tasks、quota、audit——零改动。这就是“服务契约 + 声明式装配”的扩展力：插件间只认接口不认类，换实现 = 换配置。

一个容易混淆的点

jwt_auth.py 的正常使用方式是与 auth.py 二选一：app.yml 里同一时间只有一行 id: auth。如果两个都装，第二次 ctx.provide("auth", ...) 会抛 ServiceConflict（同名服务不能双提供）——这是 Cordis 服务的显式冲突保护，防止你“不声不响地覆盖”了别人的实现。

§06一次请求的完整旅程（GET /api/tasks）

假设客户端已经启动服务，用 acme 租户创建过一条任务。现在发送： curl -H "X-Tenant: acme" -H "X-API-Key: key-acme" http://127.0.0.1:8000/api/tasks。 下面每一层由哪个插件负责、走哪段代码，全部标注。

1
uvicorn 接收请求 → FastAPI 中间件栈

CordisGateMiddleware.dispatch()（http_service.py:35）是宿主静态装的那一个。它读 request.app.state.cordis_gate：gate 存在则交给 gate，不存在则直接 call_next（比如装配失败/插件全卸完时，服务仍能响应——虽然此时没有路由）。

2
gate 第 1 步：认证（可插拔）

ctx.get("auth") 取到 AuthService → authenticate(request)：校验 x-tenant + x-api-key 匹配。通过 → 写 request.state.tenant = "acme" 并返回 None。失败 → 直接 401，停止（不会进瀑布链，更不会命中路由）。

3
gate 第 2 步：进入 http/request 瀑布链

ctx.waterfall("http/request", tenant, request, fallback=lambda *args: call_next(request))。参数（tenant、request）被传递给链上每个监听器，fallback 是链尾：没有监听器拦截、或所有监听器都调用了 next() 时，执行最后一环。

4
quota.check 作为链上第一（也是唯一）环节

tenant 非 None → 固定窗口计数：未超 limit=5 → return next_() 放行；超了 → 直接返回 429，链短路，call_next 永远不会被调用。

5
fallback：call_next(request)

控制权交回 FastAPI/Starlette，按路由表匹配 GET /api/tasks → 命中 list_tasks（tasks.py:35，由 tasks 插件注册）。

6
list_tasks：按租户取存储 + 分页 + 埋点

registry.store(request.state.tenant) → 经 ("acme","tasks") 这个 realm 键拿到 acme 的 TaskStore → .list() → 截取 page_size=20 → bump("tasks.list")（若 metrics 插件在）→ JSONResponse。

7
响应：FastAPI 原路返回

call_next(request) 拿到 handler 的 Response 后原路返回，gate 与中间件如实传递。响应体示例：{"items":[{"id":"acme-1","title":"写文档","priority":2,"status":"open","tenant":"acme"}],"count":1}。

§07六个核心机制深挖

前六节是“是什么”，这一节回答“为什么成立”。每个机制都指出它在源码里的实现位置，让你不仅会用，还能说出原理。

7.1 响应式依赖：为什么 tasks 排在 http 前面还能工作？

触发链
Loader.include(app.yml) → 逐条 _start_entry → context.plugin(plugin, config) 创建 Fiber → fiber.refresh() 评估依赖。
软等待
dependency 未满足时 target=None，Fiber 停在 PENDING，fiber.unsatisfied 可查“在等谁”。不报错——等待是合法状态。
触发激活
提供者 provide() 时（且其 fiber 已 ACTIVE）→ _notify([name]) → 遍历所有挂起纤维，谁 inject 了该名字就 refresh() → 目标可满足 → _reload()（LOADING → 执行插件 → ACTIVE）。

所以 app.yml 里 tasks 先装，不会崩：它只是“等着”。等 http 提供 routes、tenant 提供 tenants 后，tasks 自动激活、此时才真正注册路由。**装配顺序无关**是响应式设计的直接推论——新增一个依赖更深的插件，也只需要在配置里加一行，不用考虑它排在谁的前面。

现场验证

启动日志会显示：http/tasks 的启动顺序与 app.yml 的物理顺序相反（tasks 最后才打“已激活”）。也可以在 REPL 里：loader.fibers["tasks"].state → active；若故意注释掉 http 段重启，该值保持 pending 且 unsatisfied = {"routes": "missing", "tenants": ...}。

7.2 可逆效果：为什么必须是 ctx.effect(lambda: undo)？

cordis 语义（极易踩坑）python
# ❌ 错：effect 会立即执行回调，把返回值当作“卸载逻辑”收集
ctx.effect(lambda: undo())   # 立即调用了 undo！且返回 None → 什么都没被登记
ctx.effect(undo)            # 立即调用了 undo（把 undo 当回调执行）→ 同样立即反注册

# ✅ 对：回调只是“产出”卸载函数，返回它即可
ctx.effect(lambda: undo)   # 立即执行 lambda（返回 undo 本身），fiber 后来 LIFO 调用 undo()

实现（fiber.py effect()）：result = callback() 先立即执行回调；返回值若是可调用对象则登记为 disposer。所以 “注册”这个动作本身就是干净的：不立即产生副作用，只是把关于如何撤销副作用的函数交给 fiber。卸载时 _unload() 按登记顺序逆序执行——先装的后拆，符合资源管理直觉。

为什么“单向 Listener”也要登记？

因为在 cordis 里一切动态注册默认是可逆的：ctx.on(...) 内部自己 fiber.add_effect(undo)；ctx.provide(...) 也返回 undo（卸载时 _remove_fiber_services 统一清）。于是“插件卸载 = 无残留”不是文档承诺，是机制保证——开发时少一类“为什么我改了哪里还保留着”的 bug。

7.3 waterfall：中间件链长什么样？

对比 Node 生态：Koa 的洋葱模型、Connect 的 next()。cordis 把链定义为事件：ctx.waterfall(event, *args, fallback) 收集该事件的监听器，依次调用 listener(*args, next)。每个监听器自己决定是否 next()；不调 = 拦截。链尾 = fallback（HTTP 场景就是真实处理）。

context.py · _run_waterfall（语义核心）python
async def run(index: int, values: tuple[Any, ...]) -> Any:
    if index >= len(listeners):
        if fallback is None: return None
        return await await_maybe(fallback(*values))   # 链尾
    listener = listeners[index]
    def next_fn(*next_args):
        # 无参调用 next() 沿用当前参数，与 Node 中间件语义一致
        return run(index + 1, next_args if next_args else values)
    result = listener.handler(*values, next_fn)
    return await await_maybe(result)

本例中 http/request 只有 quota 一个监听器，链 = [quota.check] → fallback → call_next。要想加“签名校验”“IP 黑白名单”“请求追踪”，都是再写一个插件 + ctx.on("http/request", ...)——不用改 http 插件，也不用改 FastAPI 中间件栈。

7.4 realm 隔离：globex 为什么“看不到” acme 的任务？

ctx.isolate(name, realm) 返回子上下文，其 _isolation[name] = realm。服务查找键 _service_key(name) = (self._realm_for(name), name)——键里带了 realm。所以：

  • scoped_acme.provide("tasks", store_acme) → 全局键 ("acme","tasks")；
  • scoped_globex.provide("tasks", store_globex) → 全局键 ("globex","tasks")；
  • scoped_globex.get("tasks") → 用自身的 realm 解析 → 只会命中 ("globex","tasks")。不存在的键返回 None，而不是“试试别的 realm”。
为什么说这是“物理隔离”而不是“业务约定”？

传统的 WHERE tenant = current_tenant 依赖每个查询都写对 WHERE——漏写一处就串租户（bug 级漏洞）。realm 隔离下，让数据不可达的不是权限检查，而是键空间本身：查询接口拿不到别的 realm 的句柄。安全边界前置到了容器层。诚实边界：这是协调式隔离（防手滑、防插件边界），不是防恶意代码的 OS 沙箱。

7.5 契约校验：@require 是怎么工作的？

provide(version="1.0") 把版本存进 ServiceEntry；@require("tenants", ">=1.0") 用 PEP 440 specifier 做约束。评估时 _requirement_reason(name, constraints)：服务不存在 → “missing”；存在但版本不满足 → 原因字符串。此时 fiber 保持 PENDING，不构成错误——等提供方升级后再自动重评。约束可以是 specifier，也可以是 callable 谓词（如 lambda svc: hasattr(svc, "query")），可以叠加。

在这个 example 里：tenants 服务被 tasks 声明了 >=1.0 约束。假设未来 tenant 插件改到 2.0（比如引入 SQL 存储），tasks 无需改动依然满足；若某插件要求 >=2.0 而装配的是 1.x，它就安静地等待——做版本护栏，不做崩溃炸弹。

7.6 HMR：改源码不重启，为什么“安全性”有保障？

1
变更被捕获

watchdog 监听 plugins/；编辑器原子保存（临时文件+rename，如 sed -i/Vim）被 on_moved 特殊处理为“一次新建”。

2
依赖图分类

ModuleGraph（运行时 sys.meta_path 追踪 + 已加载模块 AST 补全）知道谁 import 了谁，分类 accepted / declined（对齐 Node analyzeChanges）。

3
事务式重载（回滚保护）

重载集 = 变更模块 + 受影响条目模块（拓扑序）。执行前快照插件与模块命名空间；任一失败 → 恢复快照、用旧插件重新应用。修改 quota.py 的 limit 阈值 → 只会重载 quota 一个条目。

4
现场效果

限流窗口、计数器等插件内部状态归零 = 旧实例被完整替换。如果你在 debug 一个限流 bug，改完保存后计数直接重置——记得这是特性。

边界：仅纯 Python 源码模块可热替换；__main__ 或 cordis_py 自身变更视为全量重启场景（不在范围）。HMR 不会重载宿主 main.py——改宿主需重启（这是对的：宿主是“组合点”，插件是“被组合物”）。

8.2 实验一：热更限流阈值（改配置，不重启）

把 app.yml 里 quota 段的 limit: 5 改为 limit: 3 保存——不重启，约 1 秒后（debounce 0.1s + 重读装配）生效。连续请求验证：第 4 次即 429。

为什么"改代码默认值"没用？（本示例最常见的误区）

配置在启动时被 Loader.include(app.yml) 读入一次，定格在内存的 entry.config 里。此后： (1) 改 app.yml（改值/注释/删键）——HMR 只监听 plugins/，配置文件不在监听范围，进程无感知； (2) 改 quota.py 的 config.get("limit", N) 默认值——HMR 确实重载了代码，但重载时用的仍是内存快照（含旧的 limit: 5），默认值永远轮不到； (3) 只有重启才会重新读盘，产生新快照。 所以：HMR 承诺"改代码不重启"，"改配置不重启"由同一套 API 提供——hmr.watch_config(["app.yml"])（cordis_py 内置 ConfigWatcher）+ hmr.reload_config(path)（手动触发）。它监听 app.yml 并调用 loader.include()，reconcile 对变化条目执行 fiber.update()（旧效果撤销 + 新配置重启）；config 无变化的条目是空操作。示例宿主 main.py 只有一行 app.state.config_watcher = hmr.watch_config([BASE / "app.yml"])。

§10FAQ：常见的 10 个疑问

1. 这和 FastAPI 自带的依赖注入有什么区别？
FastAPI DI 解决的是函数参数级别的注入（路由依赖），且只能在 FastAPI 内部使用；cordis 解决的是应用结构级别的组合（插件、生命周期、装配、可逆、隔离），与框架无关——换 aiohttp/Flask 只改宿主，插件不动。两者不冲突：业务路由内的临时依赖用 FastAPI DI，系统能力的编排用 cordis。
2. 为什么认证不进 FastAPI 中间件栈，而是放进 cordis 服务？
因为可替换性。FastAPI 中间件一旦 add_middleware 就写死在应用级（且启动后不可再加）；而 auth 是容器里的一个名字，换 JWT 只改配置。这是“功能作为资产”与“功能作为结构”的区别。
3. 那个静态的 CordisGateMiddleware 为什么不直接写认证逻辑？
中间件是“电线”，装 / 拆 / 换都不该动它；认证是所有请求的拦截点但不是固定逻辑。静态装入口、插件注册逻辑，保证：插件全卸载时服务仍能直通、换实现不重装中间件、中间件结构不受 HMR 影响。
4. 服务没有会怎样？所谓“软等待”是不是会挂住？
PENDING 的 fiber 不阻塞任何东西：await fiber 只等当前生命周期转换完成，不等“激活”。提供者出现前的等待是惰性注册表状态，不是线程/任务的挂起。这常被称为“声明式等待”：@inject 只是声明“我准备好时再叫我”。
5. 插件之间的循环依赖会怎样？
A inject B、B inject A，且无外部触发器：都会 PENDING 等待，不会死锁、不会报错，只是互相等（可用 fiber.unsatisfied 诊断）。架构上应避免；必要时的解法是提供第三个“协调者”插件或把共享状态提升为无依赖服务。
6. HMR 会不会把我的内存数据也“换成新实例”然后丢状态？
会——这是设计意图：插件闭包里的状态属于该插件实例，重载 = 新实例。若要跨重载保留（如计数器持久化、数据库连接池），状态要放到插件外的服务（如单独的 storage 服务）或外部存储里。这恰好逼着你把“状态归属”想清楚。
7. 为什么没有用 pydantic 模型做 Config 校验？
示例刻意保持零第三方依赖。cordis_py 支持 plugin.Config = 校验函数或 pydantic 模型（依赖 [pydantic] extra），配置错误会在装载期报出而非运行期诡异行为。生产可加。
8. 这个 example 的最小可删项是什么？
所有插件都是可选项：logger 没了 → 其他插件的 ctx.get("log") 返回 None（判空即可）；auth 没了 → 请求直通、无租户绑定（quota 也相应跳过）；metrics 没了 → 埋点消失。唯一不可删的是 http（没有 routes 就没有路由）和 tenant（business 依赖 tenant，除非把 store 改回全局单例）。
9. 写一个插件的最小模板？
def plugin(ctx, config): ... 提供用 ctx.provide、消费用 @inject（硬）/ ctx.get（可选）、监听用 ctx.on、可逆用 ctx.effect(lambda: undo)。然后 app.yml 加三行。没有基类、没有注册器、没有 import 其他插件——这就是 cordis 插件的样子。
10. 如果直接跑 python main.py 报 ImportError？
三步检查：① 确保 cordis_py 已安装（仓库根 pip install -e .，yaml/watch extras 也要装，否则 app.yml 解析和 HMR 会报缺 PyYAML / watchdog）；② pip install -r requirements.txt（fastapi/uvicorn/httpx/watchdog）；③ 在 examples/task_api/ 目录内运行——from plugins.http_service import ... 是相对示例目录的导入，Python 运行脚本时会把脚本所在目录放进 sys.path，在其他目录执行 main.py 就会找不到 plugins（可以设 PYTHONPATH 解决，但推荐按目录运行）。
